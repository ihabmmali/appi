# Triage and release planning

Read the request, state, relevant task and current release scope.

1. Deduplicate against the index. Create/update the canonical task using [TEMPLATES.md](TEMPLATES.md); preserve report source and distinguish observations from assumptions.
2. Record expected result, scope, acceptance checks, dependencies and existing authorization. Leave unresolved work proposed; ready means actionable.
3. Update task → KNOWN_ISSUES row → NEXT_RELEASE selection if requested → PROJECT_STATE if priorities changed.
4. Validate records/links and review the documentation diff before the authorized commit.

Allowed outputs: task records, index, release plan and state summary. No product fix or released-feature claim follows from intake alone.

The user can supply a plain list of desired changes. Assign IDs and draft observable acceptance checks. A candidate is not a commitment. Changing committed scope requires task/user authority and a recorded reason. Adding an item to a release plan does not authorize its implementation or publication.
